## 내가 해결한 문제

이 대회의 평가는 개별 투구의 확률 예측뿐 아니라 **투수별 성적의 순위 품질**도 반영했습니다. 따라서 단순 분류 정확도 개선만으로는 부족했고, 시간에 따른 데이터 변화와 투수별 상황 차이를 함께 다뤄야 했습니다.

원본 데이터·모델 바이너리·제출 ZIP은 제외하고, 실제 제출에서 사용한 검증 원칙을 담은 공개용 코드와 실행 안내를 정리했습니다. [코드 보기](phase2-online/)

### 최종 성과를 만든 방식

- 단발성 모델 교체 대신, 이전 제출을 기준선으로 두고 검증된 개선만 누적했습니다.

- 선수 전이, 압박 상황 workload, Beta-Binomial 확률 보정 등 서로 다른 정보 축을 결합했습니다.
- 최종 `v345`에서는 특정 Regular 리그·성장 구간·혼합 구종 프로필에 한정한 Beta-Binomial 보정을 10%만 적용해 과도한 보정을 방지했습니다.

### 코드 예시 2 — 희소 집단을 위한 Beta-Binomial 평활

데이터가 적은 선수의 단순 성공률이 과도하게 흔들리지 않도록, 관측치와 사전 확률을 결합했습니다. 최종 `v345`에서는 적용 범위를 제한하고 보정 강도도 10%로 고정했습니다.

```python
def beta_posterior(success: np.ndarray, count: np.ndarray,
                   prior: np.ndarray, concentration: float) -> np.ndarray:
    return (success + concentration * prior) / (count + concentration)

beta_delta = 0.10 * (beta_probability - base_probability)
output[beta_active] = np.clip(
    output[beta_active] + beta_delta,
    0.001,
    0.999,
)
```

### 코드 예시 3 — 제출 전 확률 계약 검사

이진 확률 예측 결과가 유한한 값이며 `[0, 1]` 범위를 벗어나지 않는지 자동으로 검사했습니다.

```python
if not np.isfinite(probabilities).all():
    raise ValueError("Predicted probabilities contain non-finite values.")
if not np.all((0.0 <= probabilities) & (probabilities <= 1.0)):
    raise ValueError("Predicted probabilities must be in [0, 1].")
```

## Phase 3 — 오프라인 해커톤 본선

### 1. 기존 모델의 중복 신호를 분리한 `outs` 보정 설계

아웃 카운트가 기존의 볼-스트라이크 카운트, 주자 수, 리그 구분과 중복되는 문제를 해결하기 위해 선형 투영으로 잔차를 만들었습니다. 이 잔차만 예측 확률에 반영해 기존 신호를 중복 증폭하지 않도록 했습니다.

### 2. 투수 × 상황 기반 Empirical-Bayes 앵커 설계

희소한 상황에서는 개별 투수의 기록을 그대로 쓰면 과적합될 수 있었습니다. 이를 완화하기 위해 공식 학습 데이터에서 미리 고정한 투수·상황별 통계를 전역 평균과 함께 사용하는 앵커를 만들었습니다.

- 경기 카운트, 주자·압박 상황, 이닝, 리그, 투수 이력 수준을 조합해 상황을 정의
- 데이터가 적은 셀은 강하게 수축하고, 충분한 이력이 있는 셀만 제한된 강도로 반영
- `Map4`와 `Stage2-4` 보정을 순차 적용해 예측 기대 점수를 조정

### 3. 재현 가능한 제출 파이프라인 구현

기존 N01 모델에 `outs → Map4 → Stage2-4`를 순서대로 결합하는 빌더를 작성했습니다.

- 기준 제출 파일의 해시를 검사해 다른 모델을 잘못 결합하는 오류 방지
- 모델 구성과 보정 개수가 기대값과 다르면 빌드를 중단하도록 방어 로직 구현
- 확률 범위, 행별 확률 합, 출력 스키마를 자동 점검
- 각 평가 행이 자신의 입력과 공식 학습 데이터만 사용하도록 규칙 적합성 확인

### 4. 성능만큼 재현성을 검증

모델 점수 외에도 제출 환경에서 실패하지 않도록 검증했습니다.

- 전체 입력, 단일 행, 셔플 입력, 분할 입력의 결과 일관성 확인
- 확률의 유한성·범위·합계 및 제출 파일 구조 검사
- 대회 서버 환경을 고려한 패키지 및 실행 방식 정리
